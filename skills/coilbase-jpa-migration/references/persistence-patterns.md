# Persistence patterns for JPA migrations

Use the relevant case to guide source inspection and acceptance checks. These are historical results for the versions, workflows and databases exercised.

## Make graph reads and writes explicit

PetClinic replaced cascade-based owner, pet and visit writes with explicit service transactions and SQL. It checked ownership in the write predicates, including visit insertion, and used a precheck for friendly duplicate-name errors while leaving the database constraint authoritative. Focused tests verified rollback after insertion, later recovery, wrong-owner rejection and one winner from competing duplicate inserts on H2 and PostgreSQL. The race checks cover those constraints and operations; snapshot and serializable behavior require their own evidence. [PetClinic migration](https://github.com/ejboy/coilbase-petclinic/blob/main/docs/migration.md)

- For a migrated aggregate, identify fields written by dirty checking, cascade order, delete/orphan behavior and the owning side. Write only intended changes, retrieve keys before dependent writes, and assert both valid and rejected committed states. Check affected-row counts when missing rows, ownership or version checks affect the outcome.
- Choose a join or bounded follow-up queries according to cardinality and workload. Preserve ordering, null semantics and page totals. With joins, check for duplicate root rows before applying pagination. With several reads, verify snapshot consistency if the contract depends on it. A transaction boundary alone leaves isolation dependent on the database and configuration.
- Verify derived search and uniqueness on the real dialect. PetClinic escaped LIKE metacharacters and used deterministic ordering. Its H2 fixture had case-insensitive name columns, while its PostgreSQL fixture used case-sensitive owner search and a lower-name unique index for pets. Separate matching fixtures were used for the two apps on each backend. PetClinic accepted per-pet/per-vet reads and omitted the Spring vet cache. Check query count and cache-dependent behavior on representative data before tuning or claiming throughput equivalence.

## Preserve generated values, flush effects and transaction intent

Stargazer is a demo that tracks GitHub repository star counts and displays their history. Its Spring Data JPA implementation was ported to CoilBase/Jdbi, replacing managed mutations with explicit updates. Its Jdbi store uses `db.withHandle` with `executeAndReturnGeneratedKeys` for the inserted project ID and maps nullable counts and timestamps deliberately. It preserves a timestamp-plus-ID history tie-breaker. An unchanged response can update project fields without inserting history; 304 advances the polling timestamp. A redirect alone left persistence failures invisible, so the packaged checks inspect saved state. [Stargazer implementations and checks](https://github.com/PVRLabs/experiments/tree/main/java/jdbi-hibernate-comparison)

- Inspect identity/sequence behavior, nullability, precision, defaults and callback-produced values. Compare write ordering and exception timing when moving from Hibernate flush to immediate SQL. Own schema migrations explicitly and test representative source-created data when in-place compatibility matters.
- Per-item `transactional` in Stargazer, with the failure caught outside the callback, preserved the exercised standalone polling isolation. A nested `RepositoryContext.transactional` on the same context and thread joins the current transaction. Separate contexts independently created from a datasource do not share transactions just because they share the pool. Inspect underlying Jdbi ownership when contexts are explicitly built around the same instance. Spring `REQUIRES_NEW` suspension, rollback-only behavior, checked-exception rules and read-only hints need explicit decisions where used. [CoilBase transaction mapping](https://github.com/PVRLabs/coilbase/blob/main/docs/spring-boot-migration.md#replace-declarative-transactions)
- Stargazer retained the fetch inside the transaction to preserve the existing operation and rollback behavior. Shorten the transaction when the business contract permits moving external work. A process-local ETag can advance before a later SQL failure; verify retry and consistency if the operation couples cache or external effects with committed data.

## Retain Hibernate when the slice benefits from its semantics

Stargazer also moved off Spring Data while keeping Hibernate. It explicitly owned the pool, sessions, transaction and session factory. Its Preview 4 Jex app left `createPrimaryDataSource()` unset so the base did not initialize a Jdbi context. The packaged diagnostic checked the actual `db()` state. Jdbi remained a transitive dependency. Check your version's lifecycle and use its existing hooks to close resources on startup failure and shutdown. Materialize the data needed by rendering within the session if the view depends on lazy associations. Keep mixed SQL/ORM writes out of the same business transaction until their coordination is established and tested. [Stargazer Hibernate lifecycle](https://github.com/PVRLabs/experiments/tree/main/java/jdbi-hibernate-comparison/coilbase-hibernate)

Treat optimistic versioning, orphan removal, callback-heavy entities, inheritance, bulk JPQL and cache-dependent workflows as source inventory items. Choose and verify mappings when the application actually relies on them.
