## Executive summary

PVR Labs Financial Engine App is a real four-module Java application under
development at PVR Labs and used here to evaluate the build experiment. This report
limits application-specific details to what is necessary for that evaluation.

`mvn-lite` can replace the Financial Engine App's `scripts/mvn` as the low-noise
command used by its `scripts/build`. The `common` build was run through both
implementations:

| Runner | Maven arguments | Exit status | Result |
| --- | --- | ---: | --- |
| Financial Engine App's `scripts/mvn` | `-pl common test` | 0 | `PASS common tests` |
| `agent-scripts/scripts/mvn-lite` | `-pl common test` | 0 | `PASS · 3.944 s` |

The retained evidence reports 102 tests, zero failures/errors/skips, and
`BUILD SUCCESS`. The experiment runner and captured wrapper output are in this
directory.

For agent-visible output, the measured results were:

- successful build: 6,753 bytes from vanilla Maven and 16 bytes from `mvn-lite`
- invalid lifecycle failure: 2,730 bytes from vanilla Maven and 873 bytes from
  `mvn-lite`
- matching exit status for every compared command

These results establish compatibility for the tested command and large output
reductions for the two measured scenarios. They do not yet establish compatibility
or diagnostic parity for every Maven failure category.

Run 2 repeated those commands with the updated failure summaries. Successful output
was unchanged, while invalid-lifecycle output fell from 873 to 228 bytes and remained
actionable. Run 2 confirms that `mvn-lite` is ready to replace the application's
existing low-noise Maven helper. Broader failure-corpus testing should continue as
validation of `mvn-lite`, not as a prerequisite for maintaining two wrappers.

Run 3 validated the completed replacement through the application's installed
`./scripts/build common` path. It exited 0 and emitted 16 bytes:
`PASS · 4.240 s`. A sandbox-induced Surefire failure also supplied the missing
real-application evidence for bounded immediate-cause extraction before the same
build passed with normal filesystem permission. The adoption experiment is
therefore concluded; broader failure-corpus work belongs to ongoing `mvn-lite`
product validation.

## Conclusion

The application successfully adopted the vendored `mvn-lite` 0.1.0 script. Its
normal `./scripts/build common` command passed with one-line, 16-byte output, and a
real Surefire environmental failure produced a bounded summary containing both the
failed goal and its immediate cause while retaining the complete raw log. The
legacy helper comparison is complete. Future failure-corpus testing belongs to
ongoing `mvn-lite` product validation.

## Research questions

The experiment asks:

1. Can `mvn-lite` accept the Maven arguments generated by the application's
   `scripts/build` wrapper and preserve Maven's exit status?
2. How much agent-visible output does `mvn-lite` produce compared with the existing
   low-noise helper and vanilla Maven?
3. Does the compact failure output retain enough evidence for an agent to take the
   next diagnostic or corrective step?
4. What should be improved before the application adopts `mvn-lite`?

The experiment answered the compatibility and adoption questions for the tested
application workflow. It also produced real-application evidence for bounded
immediate-cause extraction during a Surefire environmental failure. Broader
compiler, test, dependency, plugin, and fallback coverage remains ongoing
`mvn-lite` product validation rather than an application-adoption requirement.

## Systems under comparison

### Vanilla Maven

The project's pinned Maven Wrapper, invoked with batch mode, transfer-progress
suppression, and color disabled. Output is streamed normally and is not quieted.

### Existing low-noise helper

The application's former `scripts/mvn` wrapper, used as the Run 1 and Run 2
comparison baseline. It invokes `./mvnw` with `-q -B -ntp`, buffers output, retains
logs, preserves Maven's status, and prints a bounded failure summary or log tail.

### `mvn-lite`

The candidate generic wrapper from the PVR Labs `agent-scripts` project. In compact
mode it invokes the project Maven Wrapper with `-B`, `-ntp`, and
`-Dstyle.color=never`, buffers the full raw output, preserves Maven's status, and
prints a classified summary. It retains failure logs and deletes successful logs
unless `--keep-log` is supplied.

The comparison is intentionally between agent-facing policies, not identical Maven
argument lists. In particular, the existing helper uses Maven's `-q`; `mvn-lite`
captures non-quiet Maven output privately so it has more evidence to classify while
still keeping agent-visible output compact.

## Experimental method

### Controls

- All variants used the same application checkout, Maven Wrapper, Java runtime,
  module, test suite, and local dependency cache.
- Commands were run from the application repository root.
- The success scenario used the same Maven selection and lifecycle arguments:
  `-pl common test`.
- The failure scenario used the same deliberately invalid lifecycle phase:
  `definitely-not-a-maven-phase`.
- Combined stdout and stderr were measured after each process exited.
- Exit status was recorded separately from output size.
- Runs were sequential on the same machine.
- No application source or build script was changed.

### Logical commands

Paths are represented by placeholders because repository locations are not relevant
to the comparison.

```bash
# Successful build
./mvnw -B -ntp -Dstyle.color=never -pl common test
BUILD_LABEL="common tests" ./scripts/mvn -pl common test
<agent-scripts>/scripts/mvn-lite -pl common test

# Invalid lifecycle failure
./mvnw -B -ntp -Dstyle.color=never definitely-not-a-maven-phase
BUILD_LABEL="invalid lifecycle experiment" \
    ./scripts/mvn definitely-not-a-maven-phase
MVN_LITE_LOG_DIR=<temporary-log-directory> \
    <agent-scripts>/scripts/mvn-lite definitely-not-a-maven-phase

# Output measurements
wc -c <stdout-file>
wc -c <stderr-file>
wc -w <stdout-file>
wc -w <stderr-file>
wc -l <stdout-file>
wc -l <stderr-file>
```

The application-level `scripts/build common` command maps to
`scripts/mvn -pl common test`. The experiment invoked the helper arguments directly
so each implementation received the same application-selected Maven scope.

### Measurement

For each process:

```text
agent-visible bytes = bytes(stdout) + bytes(stderr)
agent-visible words = words(stdout) + words(stderr)
agent-visible lines = lines(stdout) + lines(stderr)
estimated tokens = ceil(agent-visible bytes / 4)
```

Bytes are the primary metric because they are exact and tokenizer-independent.
The token figure is an approximation for reasoning about context consumption; it
is not an API usage or billing measurement.

### Diagnostic-quality gate

An output reduction counts as useful only when:

- the process exit status is preserved
- success or failure is unambiguous
- a recognized failure identifies its actionable subject
- a compact failure points to the retained complete raw log
- secrets supplied in Maven arguments are not echoed

The size metric alone is insufficient. A smaller output that forces an immediate
full rerun or hides the failing test, source location, dependency, or command error
is a diagnostic regression.

## Why it works with `scripts/build`

`scripts/build` changes to the Financial Engine App repository root before
invoking its Maven helper. From there, `mvn-lite` finds and uses the project's
executable `./mvnw`.

Every argument shape generated by `scripts/build` is ordinary Maven syntax supported
by `mvn-lite`:

- reactor selection: `-pl`, `-am`
- lifecycle phases: `clean`, `test`, `verify`, `package`
- test selection: `-Dtest=...`, `-Dit.test=...`
- skip/failure policy properties
- forwarded Maven arguments

The build wrapper's own `--full` option already bypasses the helper and invokes
`./mvnw`, so its behavior would remain unchanged.

## Differences from the former helper

This is command-compatible but not output-policy-identical:

- The former helper prints `BUILD_LABEL`, such as `PASS common tests`.
  Unmodified `mvn-lite` prints `PASS · <Maven total time>`.
- The former helper retains all logs under `.build-logs/maven/`.
  `mvn-lite` defaults to `.agent-logs/maven/` and deletes successful logs unless
  `--keep-log` is supplied.
- `mvn-lite` adds `-B`, `-ntp`, and `-Dstyle.color=never` in compact mode. It does
  not add the former helper's `-q`, allowing its private raw log to contain useful
  lifecycle, timing, and test evidence.
- `mvn-lite` preserves Maven's exit status and retains failure logs. Its own
  fixture suite also passed during this experiment.

## Findings and actions from Run 1

Run 1 identified the following possible improvements and migration decisions.
Their final disposition is recorded below.

### 1. Shorten verbose Maven command errors

**Disposition: Implemented and validated in Run 2.**

The invalid-lifecycle summary repeats Maven's complete list of lifecycle phases.
That information increased the measured `mvn-lite` failure output to 873 bytes even
though the actionable evidence is only:

```text
Maven: Unknown lifecycle phase "definitely-not-a-maven-phase"
```

Run 1 proposed keeping the complete message in the retained raw log while reducing
the compact summary to the first actionable sentence. The expected result was a
substantially larger token reduction than the measured 37.3% while preserving
diagnostic value.

### 2. Preserve an optional build label

**Disposition: Deferred.** Label-free success output was explicitly accepted as
part of the application migration. Project-specific build vocabulary remains
outside the generic wrapper.

The former helper prints a useful scope label:

```text
PASS common tests
```

Unmodified `mvn-lite` prints:

```text
PASS · 3.944 s
```

The outputs differ by only two bytes in this experiment, so removing the scope
provides no meaningful efficiency gain. Run 1 proposed an optional generic
environment variable such as `MVN_LITE_LABEL`, which would allow the application
wrapper to produce:

```text
PASS common tests · 3.944 s
```

The migration explicitly accepted label-free output, so this proposal was not
required for adoption.

### 3. Improve immediate-cause extraction

**Disposition: Implemented in Run 2 and validated against a real Surefire
environmental failure in Run 3.**

When a Maven plugin goal fails before emitting a standard compiler or test failure,
the compact output may contain only the plugin goal. During an environmental
Surefire failure, for example, the raw log contained an actionable
`Unable to create temporary directory` cause that was absent from the compact
summary.

Run 1 proposed recognizing the immediate cause from standard
`Failed to execute goal ... failed:` messages and including a bounded `Cause:`
entry, while keeping the raw log authoritative and avoiding reconstruction of
arbitrary exception chains.

### 4. Add output-size regression tests

**Disposition: Implemented for the bounded Maven-command and plugin-cause forms
added during this experiment. Broader category coverage remains ongoing product
validation.**

The fixture suite already checked diagnostic content and bounded unknown-failure
tails. Run 1 proposed extending it with maximum byte budgets for:

- compiler failures
- unit- and integration-test failures
- dependency-resolution failures
- Maven command errors
- plugin failures with an immediate cause
- unknown failures using the log-tail fallback

Byte budgets should supplement, not replace, assertions that the actionable
diagnostic and raw-log path are present.

### 5. Benchmark the complete failure corpus

**Disposition: Deferred from the application-adoption gate.** Future corpus work
should validate the reusable `mvn-lite` product rather than preserve two
application wrappers for comparison.

Run 1 proposed comparing both implementations against the fixed failure corpus
described in the token-efficiency section below before replacement. The initial
success and invalid-phase results were encouraging, but did not establish that
every failure category was both smaller and equally useful.

### 6. Adopt failure-only log retention

**Disposition: Accepted and adopted.** Successful logs are deleted by default,
failed logs are retained, and `--keep-log` remains available for explicit
successful-log retention.

Run 1 proposed retaining every failed compact-build log and deleting successful
logs by default, with `--keep-log` reserved for flaky-test investigations, timing
comparisons, or explicit audit needs.

It also proposed adding `.agent-logs/` to the application's `.gitignore` and
updating its agent guidance, with `MVN_LITE_LOG_DIR` used only if preserving the
existing failure-log location justified a project-specific setting.

### Run 1 outcome

1. Verbose Maven command errors were shortened.
2. Bounded immediate-cause extraction was added.
3. Focused fixture and byte-budget tests were added.
4. Label-free success output was explicitly accepted.
5. Failure-only log retention was adopted.
6. The application replaced its legacy helper with the shared `mvn-lite`.
7. Broader failure-corpus work was moved to ongoing product validation.

During Run 1, no Financial Engine App source or script was changed. Maven updated
normal incremental files under `common/target`, and the project remained
git-clean.

## Run 1 agent token-efficiency comparison

The primary metric is the total UTF-8 bytes written to stdout and stderr because it
is exact, reproducible, and independent of a particular model tokenizer. Words and
lines are useful secondary measures. Estimated tokens use the common approximation
of four UTF-8 bytes per token:

`estimated tokens = ceil(total output bytes / 4)`

This estimate is suitable for comparing output sizes, but it is not an API billing
measurement. Exact token counts vary by model tokenizer, paths, Maven versions, and
the specific failure text.

### Measurements

| Scenario | Runner | Status | Bytes | Words | Lines | Estimated tokens |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| Successful `common` tests | Vanilla Maven | 0 | 6,753 | 684 | 90 | ~1,689 |
| Successful `common` tests | Existing helper | 0 | 18 | 3 | 1 | ~5 |
| Successful `common` tests | `mvn-lite` | 0 | 16 | 4 | 1 | ~4 |
| Invalid lifecycle phase | Vanilla Maven | 1 | 2,730 | 200 | 35 | ~683 |
| Invalid lifecycle phase | Existing helper | 1 | 1,393 | 133 | 20 | ~349 |
| Invalid lifecycle phase | `mvn-lite` | 1 | 873 | 72 | 9 | ~219 |

For successful builds, the wrappers are effectively tied; the two-byte difference
is not operationally meaningful. Both reduce successful output by more than 99.7%
relative to vanilla Maven.

For the measured failure, `mvn-lite` saved:

- 520 bytes, or 37.3%, relative to the existing helper
- 1,857 bytes, or 68.0%, relative to vanilla Maven
- roughly 464 estimated tokens relative to vanilla Maven

It also reduced vanilla Maven's 35 output lines to 9. The existing helper is already
compact, so the comparison against it measures the incremental benefit of
`mvn-lite`; the vanilla comparison shows the total benefit of using a low-noise
agent-facing wrapper.

Vanilla Maven was invoked through the same project Maven Wrapper with `-B`, `-ntp`,
and `-Dstyle.color=never`, matching `mvn-lite`'s compact-mode output settings. It was
not given `-q`, because the purpose of this baseline is to measure ordinary Maven
output rather than another quiet-output policy.

### How to measure well

Use a fixed corpus of commands and run every wrapper against the same project state.
At minimum, include:

- a successful unit-test build
- a compiler failure
- a unit-test assertion failure
- an integration-test failure
- a dependency-resolution failure
- an invalid goal or lifecycle phase
- an unrecognized failure that exercises the bounded log-tail fallback

For every run, record:

- process exit status
- combined stdout and stderr bytes, words, and lines
- estimated tokens
- whether the output identifies the actionable failure
- whether the complete raw log is retained

Token reduction is only useful when diagnostic quality is preserved. A concise
output that omits the failing test, source location, dependency, or raw-log path
should not count as a win.

The included `extras/run-1/measure-agent-output.sh` script reports exact size
metrics and the four-bytes-per-token estimate for captured output files.

## Threats to validity and limitations

- **Sample size:** Each reported command was measured once. The byte counts are
  deterministic for those captured outputs, but the experiment does not report
  variance.
- **Warm incremental build:** The successful run used the existing incremental
  build state and local Maven cache. This is appropriate for agent iteration but
  does not represent a clean or cold-cache build.
- **Limited scenarios:** Only one successful module build and one synthetic Maven
  command error were compared across all three runners.
- **No timing claim:** Maven total time was observed but not benchmarked. The
  experiment makes no performance or wall-clock efficiency claim.
- **Approximate tokens:** The four-bytes-per-token conversion is not an exact count
  for a specific model. Paths, punctuation, and tokenizer choice affect the result.
- **Path-length sensitivity:** Retained-log paths contribute to failure-output
  bytes. Different checkout paths will change absolute counts slightly.
- **Diagnostic judgment:** Actionability is partly qualitative. The broader corpus
  should define required evidence for each failure class before measurement.
- **Publication scope:** Excluding source and artifact details prevents an external
  reviewer from independently reproducing this exact application build. Reviewers
  can still inspect the wrapper logic, measurement method, captured aggregate
  evidence, and reproduce the procedure against another Maven project.
- **Ordinary Maven definition:** Vanilla Maven was measured without `-q` but with
  noninteractive and presentation-related flags. A different Maven invocation may
  produce different absolute output.

## External review checklist

A reviewer should verify:

- the three logical commands represent the intended policies fairly
- exit statuses match for equivalent commands
- byte counts include both stdout and stderr
- the token estimate is clearly separated from exact measurements
- the invalid lifecycle summary remains actionable
- failure logs are retained and successful logs follow the documented policy
- no application-identifying details appear in the published artifacts
- recommendations are supported by measurements or clearly marked as proposals

For a stronger independent review, run at least five repetitions of the complete
failure corpus on a separate multi-module Maven project and report median bytes,
minimum/maximum bytes, diagnostic-gate results, Maven version, Java version, and
wrapper checksums.

## Article guidance

The final evidence supports narrowly stated claims:

- In this application experiment, `mvn-lite` reduced successful agent-visible
  output from 6,753 bytes to 16 bytes relative to vanilla Maven, a reduction of
  more than 99.7%.
- For the measured invalid-lifecycle error, updated `mvn-lite` reduced output from
  2,730 bytes to 228 bytes, a 91.6% reduction, while preserving the exit status,
  actionable phase name, full-log pointer, and rerun guidance.
- Relative to the application's existing low-noise helper, successful output was
  effectively tied, while updated `mvn-lite` reduced the measured
  invalid-lifecycle output from 1,393 bytes to 228 bytes, an 83.6% reduction.
- Run 3 validated the installed application integration and demonstrated bounded
  immediate-cause extraction against a real Surefire environmental failure.

The current evidence does not support claims that `mvn-lite` always saves a fixed
percentage, improves Maven execution time, or produces sufficient diagnostics for
every Maven failure. Those require the complete corpus and repeated measurements.

An article should lead with exact byte and line counts, describe estimated tokens
as an approximation, disclose the warm incremental state and single-run sample,
and link the claims to the wrapper version checksum or source revision used.

### Run 2 adoption decision

Run 2 confirms that `mvn-lite` is ready to replace the application's existing
low-noise Maven helper. The tested build command remains compatible, failure output
is materially smaller, and full diagnostics remain available in retained logs.
Broader failure-corpus testing should continue as validation of `mvn-lite`, not as
a prerequisite for maintaining two wrappers.

The replacement should explicitly document two output-policy differences:
`mvn-lite` does not consume the application's `BUILD_LABEL`, and it changes the
default successful-log location and retention policy. These are migration choices,
not blockers to replacement.
